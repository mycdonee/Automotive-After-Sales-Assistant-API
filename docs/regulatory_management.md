# Regulatory Management Milestone

## 1. Purpose

The Regulatory Management branch extends the Automotive After-Sales Assistant API beyond complaint intelligence.

The milestone demonstrates an enterprise-oriented regulatory retrieval workflow with:

- verified public regulatory sources
- structured and traceable records
- explicit data contracts
- semantic natural-language retrieval
- metadata filtering
- UNECE–FMVSS comparison support
- legal-equivalence safeguards
- typed REST and OpenAPI integration
- deterministic automated testing

The system is an information-retrieval prototype. It does not replace legal, regulatory, engineering, or compliance review.

## 2. Dataset scope

The committed dataset contains:

```text
18 regulation records
11 approved comparison pairs
3 regulatory systems
```

The three regulatory systems are:

1. braking and stability
2. occupant restraint
3. lighting and light signalling

The records cover selected:

- UNECE regulations
- United States Federal Motor Vehicle Safety Standards

Each record represents one regulation or standard.

Reviewed amendments and versions are captured in structured version and source fields rather than being stored as unrelated duplicate records.

## 3. Regulation records

Each structured regulation record includes fields such as:

- canonical regulation ID
- jurisdiction
- issuing authority
- official identifier
- aliases
- title and citation
- regulatory system
- regulated object
- scope summary
- vehicle applicability
- requirement topics
- reviewed version
- reviewed source documents
- source format
- source-content date
- review date
- special status notes
- verification status

The runtime models reject unexpected fields and invalid enumerated values.

## 4. Comparison model

Each approved comparison pair connects:

```text
one UNECE regulation
        ↕
one related United States FMVSS standard
```

A pair is approved only when the reviewed sources establish meaningful overlap in one or more of these dimensions:

- regulated vehicle system
- vehicle applicability
- regulated object
- technical requirements
- performance requirements
- test dimensions

All currently approved pairs use:

```text
status = approved
comparison_level = partial
legal_equivalence = false
```

A partial comparison means the two sources contain meaningful technical overlap but may differ in:

- scope
- definitions
- vehicle applicability
- procedures
- thresholds
- test conditions
- legal context
- implementation rules

It never means that compliance with one regulation proves compliance with the other.

## 5. Structured data artifacts

The principal artifacts are:

```text
data/regulations/regulation_records.jsonl
data/regulations/regulation_comparison_pairs.json
data/regulations/schemas/regulation_record.schema.json
data/regulations/schemas/regulation_comparison_pair.schema.json
data/regulations/data_contract.md
data/regulations/comparability_verification.md
data/regulations/README.md
```

The structured files are generated by:

```text
scripts/generate_regulation_data.py
```

They are independently checked by:

```text
scripts/validate_regulation_data.py
```

The generation and validation scripts are intentionally separate. Generated output is not trusted solely because it was produced by the project generator.

## 6. Runtime architecture

The runtime data flow is:

```text
Committed JSONL and JSON
        ↓
Pydantic runtime models
        ↓
cross-reference validation
        ↓
derived search documents
        ↓
SentenceTransformer embeddings
        ↓
cosine-similarity ranking
        ↓
typed FastAPI responses
```

### 6.1 Regulation data loader

The loader is implemented in:

```text
app/services/regulation_data_loader.py
```

It:

- reads the committed JSONL and JSON files
- validates every item using Pydantic
- rejects unexpected fields
- checks identifier uniqueness
- verifies comparison references
- verifies UNECE-left and United-States-right direction
- checks regulatory-system consistency
- constructs semantic-search documents
- returns immutable runtime models
- caches the validated dataset

The runtime loader does not read the original PDF, XML, HTML, DOCX, or TXT research files.

### 6.2 Regulation semantic search service

The semantic service is implemented in:

```text
app/services/regulation_semantic_search_service.py
```

It:

- loads the validated regulation dataset
- reuses the existing SentenceTransformer model loader
- precomputes regulation-record embeddings
- precomputes comparison-pair embeddings
- filters eligible candidates before ranking
- calculates cosine similarity
- returns typed immutable result objects
- caches the service instance within the application process

The current embedding model is:

```text
sentence-transformers/all-MiniLM-L6-v2
```

## 7. API endpoints

### 7.1 Search regulation records

```text
POST /regulations/search
```

Supported request fields:

- `query`
- `top_k`
- `jurisdiction`
- `regulatory_system`

The response contains:

- regulation ID
- official identifier
- title
- jurisdiction
- regulatory system
- regulated object
- scope summary
- reviewed version
- similarity score

### 7.2 Search comparison pairs

```text
POST /regulations/comparisons/search
```

Supported request fields:

- `query`
- `top_k`
- `regulatory_system`

The response contains:

- pair ID
- pair number
- left and right regulation IDs
- left and right official identifiers
- regulatory system
- comparison focus
- comparison level
- overlap summary
- legal-equivalence field
- similarity score

For every committed comparison result:

```text
legal_equivalence = false
```

## 8. Validation layers

The milestone applies several independent validation layers.

### 8.1 Generation-time validation

The generator verifies:

- exact record count
- exact pair count
- canonical IDs
- approved pair mappings
- reference integrity
- comparison status
- comparison level
- legal-equivalence safeguards

### 8.2 JSON Schema validation

The independent validator verifies:

- required fields
- forbidden unexpected fields
- field types
- string patterns
- allowed enumerated values
- date formats
- regulation-record schema compliance
- comparison-pair schema compliance

### 8.3 Cross-reference and contract validation

The validator checks:

- unique regulation IDs
- unique pair IDs
- unique pair numbers
- referenced regulation existence
- UNECE-left and FMVSS-right direction
- regulatory-system alignment
- canonical pair mappings
- approved verification references

### 8.4 Runtime validation

The application loader checks:

- Pydantic model validity
- unique runtime identifiers
- comparison references
- jurisdiction consistency
- regulatory-system consistency
- derived-document count consistency

### 8.5 API validation

FastAPI and Pydantic reject:

- blank queries
- queries that are too short
- invalid `top_k` values
- unsupported jurisdictions
- unsupported regulatory systems
- unexpected request fields

## 9. Testing strategy

The milestone includes tests for:

- committed structured data
- generation reproducibility
- JSON Schema validation
- contract invariants
- runtime data loading
- duplicate-ID rejection
- unknown-reference rejection
- immutable runtime models
- semantic document construction
- metadata filtering
- semantic ranking
- malformed embedding output
- FastAPI request validation
- dependency injection
- response serialization
- OpenAPI documentation
- legal-equivalence preservation

Semantic-service unit tests use deterministic fake embeddings.

API tests use a fake service through FastAPI dependency overrides.

This prevents normal automated tests from depending on:

- network availability
- Hugging Face availability
- local model-download state
- small model-version ranking changes
- local hardware differences

A separate smoke test verifies the real end-to-end path:

```text
FastAPI endpoint
→ cached semantic service
→ Hugging Face SentenceTransformer
→ structured regulation data
→ typed API response
```

## 11. Safety and legal boundaries

The API must not describe semantic similarity as:

- legal confidence
- legal equivalence
- regulatory certification
- compliance approval
- proof of interchangeability

The official legal source remains authoritative.

The comparison dataset is an analytical aid for locating technically related sources and understanding scoped overlap and differences.

## 12. Current limitations

- Only 18 selected regulations are included.
- Only 11 manually reviewed comparison pairs are included.
- The dataset does not cover every amendment, interpretation, exemption, or national implementation rule.
- Comparison summaries are not clause-by-clause legal analyses.
- Semantic ranking has not yet been evaluated with a large labelled regulatory-query benchmark.
- Embeddings are retained in application memory.
- No persistent vector database is used.
- Authentication and authorization are not implemented.
- Docker deployment and continuous integration remain future work.
